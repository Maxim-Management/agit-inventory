# AGIT tool and components track

Название сайта (заголовок вкладки браузера, шапка, футер) — **AGIT tool and
components track**. Внутри кода и в этом README система по-прежнему может
называться «АГИТ» — это на сам сервис не влияет, названия таблиц/файлов/
репозитория не переименовывались.

Онлайн-сервис для контроля остатков, поступлений и списаний компонентов
осцилляторной системы АГИТ: поступления, списания с указанием причины
(ремонт / брак / повреждение), учёт наработки серийных компонентов, подбор
оптимальной пары ротор-статор по зазору OD/ID, аналитика расхода по периодам
и прогноз заказа на 3 месяца вперёд. Все комплектующие — и серийные (роторы,
статоры, корпусные детали), и расходники россыпью (масло, уплотнения, кольца)
— учитываются единообразно: у каждой детали есть один и тот же «текущий
остаток», видимый на дэшборде, в прогнозе и в аналитике, независимо от
способа учёта. Списания и поступления вносятся только через приложение и
могут быть привязаны к конкретной ремонтной/сборочной работе — для неё
отдельно считается полная стоимость (детали + сервисный центр + персонал +
прочее) с отчётом за период. Каждый инструмент (буровая компоновка) заведён
в системе под собственным серийным номером; ремонтные/сборочные работы и
списания всегда привязываются к конкретному инструменту, а его наработка и
выручка ведутся отдельно — с автоматическим расчётом рентабельности
(выручка минус затраты на работы) для каждого серийного номера инструмента.

Сервис веб-based, многопользовательский (роли: администратор / инженер /
наблюдатель), рассчитан на развёртывание в облаке (Vercel + Supabase) с
доступом из любого места по логину и паролю.

## Стек

- **Backend**: Python 3 / Flask (server-rendered, без отдельного фронтенд-сборщика)
- **БД**: PostgreSQL в продакшне (Supabase, бесплатный тариф), SQLite — для
  локальной разработки и тестирования (переключение автоматическое по
  переменной окружения `DATABASE_URL`)
- **Хостинг**: Vercel (бесплатный тариф, Python-функции)
- **Аутентификация**: собственная, на сессиях Flask (email/пароль,
  пароли хранятся хешированными), + защита от CSRF
- **UI**: Tailwind CSS и Chart.js подключаются через CDN — сборка фронтенда
  не требуется

Почему не Next.js/Node: важнее было получить полностью рабочее и
протестированное приложение (реальная проверка каждого сценария — поступления,
списания, подбор пар, аналитика, прогноз — были прогнаны локально с вашими
исходными данными). Всё это отлично разворачивается на Vercel + Supabase, как
и договаривались, просто на стороне бэкенда используется Python/Flask вместо
Node.

## Структура проекта

```
app/                  — код приложения (Flask blueprints, шаблоны, бизнес-логика)
  matching.py          — подбор пары ротор/статор (венгерский алгоритм)
  analytics.py         — аналитика по периодам + прогноз заказа на 3 мес.
  stock.py              — единый расчёт текущего остатка для ЛЮБОЙ детали
  jobs.py                — ремонтные/сборочные работы и стоимость
  tools.py                 — реестр инструментов, наработка/выручка/рентабельность на серийный номер
  db.py                   — слой доступа к БД (SQLite локально / PostgreSQL в проде)
api/index.py           — точка входа для Vercel (Python serverless function)
scripts/
  init_db.py            — создание таблиц БД (свежая установка)
  create_admin.py        — создание первого администратора
  import_excel.py        — импорт данных из вашего исходного Excel-файла
  dedupe_receipts.py      — разовый скрипт: находит и (с флагом --apply) удаляет точные дубликаты записей о поступлении; запускать ДО migrate_receipt_batches.py
  migrate_receipt_batches.py — разовый скрипт: после миграции 0008 восстанавливает остатки по партиям (receipts.remaining_quantity) и привязку серийных единиц к партии (units.receipt_id) для данных, существовавших до перехода на партийную модель
migrations/
  0002_unified_stock_and_service_jobs.sql — миграция для уже развёрнутой БД
  0003_tools.sql                          — миграция: реестр инструментов, привязка работ и наработка/выручка на серийный номер
  0004_receipt_batch_details.sql          — миграция: детали партии поступления (дата произв., пошлина %, курс, стоимость CNY, серийный № партии)
  0005_job_order_fields.sql               — миграция: номер наряд-заказа, исполнитель, сервисный центр (наименование) для ремонтных/сборочных работ
  0006_usage_log_admin_controls.sql       — миграция: связь записей наработки компонента с записью наработки инструмента (для корректного редактирования/удаления администратором)
  0007_unit_cost_formula.sql              — миграция: курс юаня и пошлина в карточке детали, трансфер прайс за единицу в поступлении (расчётная стоимость за единицу)
  0008_receipt_batches.sql                — миграция: поступления как партии с собственным остатком (remaining_quantity), привязка серийной единицы к партии (units.receipt_id), привязка списания к партии (write_offs.receipt_id) — см. «Партии поступления» ниже; после её применения к уже работающей БД запустите scripts/dedupe_receipts.py, затем scripts/migrate_receipt_batches.py
  0009_duty_on_part_and_tool_cost.sql     — миграция: таможенная пошлина переносится с партии на позицию (удаляет receipts.customs_duty_percent, пошлина остаётся только в parts.customs_duty_percent), добавляет себестоимость инструмента (tools.cost_rub) для расчёта амортизации
  0010_customers_and_revenue_details.sql  — миграция: справочник заказчиков (customers) и расширение выручки инструмента (заказчик, номер скважины, часы работы, сутки дежурства, снимок ставок, ссылка на перенесённую наработку) — см. «Заказчики» ниже
schema_postgres.sql      — актуальная схема БД для PostgreSQL (Supabase, свежая установка)
schema_sqlite.sql        — та же схема, адаптированная под SQLite (только для локальной разработки)
vercel.json               — конфигурация развёртывания на Vercel
requirements.txt          — зависимости Python
```

## Быстрый локальный запуск (для проверки перед деплоем)

В архиве уже есть готовая локальная база `data/agit.db` с импортированными
данными из вашего Excel-файла и одним администратором для входа:

- Email: `admin@agit.local`
- Пароль: `ChangeMe2026!` (смените сразу после первого входа — ссылка со
  своим именем в правом верхнем углу любой страницы -> «Смена пароля»)

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

python run.py                 # http://localhost:5000 — сразу с демо-данными
```

Если нужно начать с чистой базы (например, чтобы перепроверить импорт или
начать без демо-пароля по умолчанию):

```bash
rm data/agit.db
cp .env.example .env          # без DATABASE_URL — будет использована SQLite
python scripts/init_db.py
python scripts/import_excel.py "1. AGIT Spares and Components.xlsx"
python scripts/create_admin.py you@company.com "Ваше имя"   # выведет временный пароль
python run.py
```

## Развёртывание в облаке (Vercel + Supabase, бесплатные тарифы)

### 1. Создайте проект Supabase (база данных)

1. Зарегистрируйтесь на [supabase.com](https://supabase.com) и создайте новый проект (Free tier).
2. Откройте **SQL Editor** и выполните содержимое файла `schema_postgres.sql` целиком (создаст все таблицы).
   Если вы уже разворачивали более раннюю версию сервиса, вместо этого выполните
   по порядку файлы из `migrations/`, которых у вас ещё не было — каждый
   безопасно дополняет уже существующие таблицы, ничего не удаляя:
   - `0002_unified_stock_and_service_jobs.sql` — учёт расходников и ремонтные работы;
   - `0003_tools.sql` — реестр инструментов (серийные номера), привязка работ и
     компонентов к инструменту, наработка/выручка на инструмент;
   - `0004_receipt_batch_details.sql` — справочные поля партии поступления
     (серийный № партии, дата производства, таможенная пошлина %, курс
     валюты, общая стоимость в CNY);
   - `0005_job_order_fields.sql` — номер наряд-заказа, исполнитель
     (супервайзер), наименование сервисного центра для ремонтных/сборочных
     работ;
   - `0006_usage_log_admin_controls.sql` — связывает запись наработки
     компонента с породившей её записью наработки инструмента, чтобы
     редактирование/удаление наработки администратором корректно
     пересчитывало часы компонентов;
   - `0007_unit_cost_formula.sql` — курс юаня к рублю и пошлина (%) в
     карточке детали, трансфер прайс за единицу в поступлении — для расчёта
     стоимости за единицу по формуле (см. «Расчётная стоимость за единицу»
     ниже).
   - `0008_receipt_batches.sql` — поступления как партии с собственным
     остатком, привязка серийной единицы и списания к партии (см. «Партии
     поступления» ниже). **Если на этой базе уже есть реальные данные**
     (не первое развёртывание), сразу после выполнения этого файла в SQL
     Editor запустите ещё два разовых скрипта с компьютера, указав ту же
     `DATABASE_URL`, что и у Supabase (по аналогии с шагом 5 ниже,
     «Импортируйте исходные данные»):
     ```bash
     export DATABASE_URL="postgresql://...."
     python scripts/dedupe_receipts.py            # сначала — сухой прогон, посмотреть, что найдено
     python scripts/dedupe_receipts.py --apply     # затем, если дубликаты есть — реально удалить их
     python scripts/migrate_receipt_batches.py     # и только теперь — разово восстановить остатки по партиям
     ```
     Для свежей установки (данные загружаются через `import_excel.py`, шаг
     5 ниже) эти два скрипта не нужны — свежий импорт уже создаёт партии и
     их остатки корректно.
   - `0009_duty_on_part_and_tool_cost.sql` — удаляет колонку таможенной
     пошлины у партии (`receipts.customs_duty_percent`) — теперь пошлина
     хранится только в карточке детали (`parts.customs_duty_percent`) и
     одна и та же для всех партий этой детали — и добавляет себестоимость
     инструмента (`tools.cost_rub`) для расчёта начисленной амортизации
     (см. «Инструменты» ниже). Разовых скриптов после неё запускать не
     нужно — оба новых расчёта (стоимость по партиям с пошлиной из карточки
     детали, амортизация инструмента) уже написаны так, что работают сразу
     после применения миграции, без переноса исторических данных.
   - `0010_customers_and_revenue_details.sql` — создаёт справочник
     заказчиков (`customers`: название, номер договора, ставка за час
     работы, ставка за сутки ожидания/дежурства) и добавляет в
     `tool_revenue` поля заказчика, номера скважины, часов работы, суток
     дежурства, снимка применённых ставок и ссылки на автоматически
     перенесённую наработку (см. «Заказчики» ниже). Разовых скриптов после
     неё запускать не нужно — старые записи выручки (без заказчика)
     продолжают работать как раньше.
3. Нажмите кнопку **Connect** (вверху страницы проекта) и выберите режим
   **Transaction pooler** (порт 6543) — именно он рекомендован Supabase для
   serverless-платформ вроде Vercel (короткие изолированные подключения на
   каждый запрос, как раз наш случай). Если в интерфейсе вместо вкладок вы
   видите просто одну строку подключения — по умолчанию это обычно и есть
   Transaction pooler; сверьте порт в строке — должен быть `:6543`.
   Скопируйте строку подключения — понадобится на следующем шаге.

### 2. Разместите код в GitHub

Загрузите содержимое этого архива в новый репозиторий GitHub (можно через
веб-интерфейс GitHub — "Upload files", без командной строки).

### 3. Разверните на Vercel

1. Зарегистрируйтесь на [vercel.com](https://vercel.com) (можно через GitHub).
2. **Add New -> Project**, выберите ваш репозиторий.
3. Если на экране импорта есть раздел **Environment Variables** — добавьте в
   нём `SECRET_KEY` (случайная строка, см. пример генерации в
   `.env.example`) и `DATABASE_URL` (строка подключения из Supabase, шаг
   1.3) и нажмите **Deploy**. Если такого раздела нет (интерфейс Vercel
   периодически меняется) — это не проблема: нажмите **Deploy** сразу как
   есть (первый деплой может завершиться с ошибкой из-за отсутствия
   переменных — это ожидаемо) и добавьте переменные следующим шагом.
4. Откройте созданный проект -> вкладка **Settings** -> раздел
   **Environment Variables** (это надёжный путь, который не зависит от
   версии интерфейса Vercel). Добавьте по одной переменной за раз:
   `SECRET_KEY` и `DATABASE_URL` (значения те же, что в пункте 3), для
   каждой оставьте все окружения (Production/Preview/Development)
   отмеченными, и нажмите **Save**.
5. Передеплойте: вкладка **Deployments** -> у самого верхнего (последнего)
   деплоя нажмите на **⋯** справа -> **Redeploy**. Новые переменные
   применяются только к новым деплоям, поэтому этот шаг обязателен даже
   если первый деплой уже был успешным.

### 4. Создайте первого администратора

Есть два способа — выбирайте любой.

**Способ А — прямо в браузере, без терминала и без Python.** Откройте адрес
вашего сайта и допишите `/setup` (например
`https://ваш-проект.vercel.app/setup`). Пока в базе нет ни одного
пользователя, эта страница покажет форму «Первая настройка» — укажите email,
имя и пароль, и вы сразу окажетесь внутри под ролью «Администратор». Как
только первый пользователь создан (этим способом или следующим), страница
`/setup` сама перестаёт открываться — она разовая, из соображений
безопасности.

**Способ Б — через терминал**, если по какой-то причине нужен более
предсказуемый способ (например, для автоматизации): выполните скрипт
создания администратора, указав ту же `DATABASE_URL`, что и в Vercel (можно
с любого компьютера, где установлен Python — соединение с Supabase идёт
напрямую по интернету):

```bash
pip install -r requirements.txt
export DATABASE_URL="postgresql://...."   # значение из Supabase
python scripts/create_admin.py you@company.com "Ваше имя"
```

Скрипт выведет временный пароль — войдите под ним. Дополнительных
пользователей в любом случае удобнее заводить уже из интерфейса — раздел
**Пользователи** (виден только роли «Администратор»).

### 5. Импортируйте исходные данные (один раз)

```bash
export DATABASE_URL="postgresql://...."
python scripts/import_excel.py "1. AGIT Spares and Components.xlsx"
```

Импортируются: справочник деталей, серийные компоненты (включая OD/ID для
роторов/статоров, наработку и статус «на складе» / «установлен»), история
поступлений по колонкам «Received on ... as per order N», а для расходников
россыпню (масло, уплотнения, кольца и т.п.) — остаток на дату среза (см.
раздел «Единый учёт остатков» ниже) и цена за единицу в рублях (для отчёта
по стоимости работ). Деталь считается серийной автоматически, если для неё
есть карточки в листе «AGIT components» — остальные становятся
количественными. Из колонки «Installed on tool» того же листа дополнительно
создаётся реестр инструментов (раздел **Инструменты**, см. ниже) — по одной
записи на уникальный серийный номер инструмента, с привязкой к нему всех
компонентов, которые на нём числятся установленными на момент импорта. Лист
«AGIT Spares write-off» в исходном файле фактически описывает не
брак/ремонт/повреждение, а расход деталей на сборку инструментов — это уже
отражено через статус «установлен» у соответствующих единиц, поэтому
отдельно не дублируется. Таблица списаний с причинами (ремонт/брак/
повреждение) стартует пустой и будет наполняться в процессе эксплуатации
через интерфейс.

Готово — сервис доступен по адресу, который выдаст Vercel (вида
`https://ваш-проект.vercel.app`), с любого устройства, по логину и паролю.

## Роли пользователей

- **Администратор** — полный доступ, включая управление пользователями и справочником деталей.
- **Инженер** — может вносить поступления, списания, наработку, подтверждать
  пары ротор/статор, регистрировать инструменты, устанавливать/снимать на
  них компоненты, вносить наработку и выручку инструментов, создавать
  ремонтные/сборочные работы.
- **Наблюдатель** — только просмотр (отчёты, остатки, аналитика, прогноз).

Склад один общий — роли определяют права действий, а не видимость данных
(так, как вы и указали при постановке задачи).

**Только администратору** доступны: удаление ремонтных/сборочных работ,
редактирование их прочих затрат (сервисный центр/персонал/прочее), а также
редактирование и удаление уже внесённых записей наработки и выручки — как
на странице инструмента, так и на странице отдельного серийного компонента.
Записи наработки компонента, появившиеся автоматически как «зеркало»
наработки инструмента, редактируются/удаляются только на странице
инструмента — с автоматическим пересчётом у всех затронутых компонентов.

## Раздел «Комплектующие»

Единый раздел вместо двух отдельных ( ~~«Детали»~~ и ~~«Серийные
компоненты»~~ ): и серийные компоненты (роторы, статоры, корпусные
детали — каждый со своим серийным номером), и несерийные расходники
(масло, уплотнения, кольца и т.п.) показаны в одной таблице, в порядке
столбцов: **типоразмер, наименование, партийный номер, серийный номер,
статус, наработка, применение на инструменте, комментарии**.

- Для серийного компонента строка = конкретная физическая единица: статус
  («на складе» / «в эксплуатации» / «в паре» / «списан»), фактическая
  наработка в часах, ссылка на инструмент, на котором он установлен (если
  установлен), и заметки по этой единице.
- Для несерийного расходника строка = одна на деталь (серийного номера у
  него нет — в столбце стоит прочерк): в столбце «Статус» вместо статуса
  единицы показан текущий остаток (подсвечивается красным при остатке ниже
  неснижаемого), столбцы «Наработка» и «Применение на инструменте» для
  таких строк неприменимы (прочерк), в «Комментарии» — спецификация детали.
- Поиск ищет по наименованию, партийному и серийному номеру; фильтры — по
  типоразмеру и по статусу (статус применим только к серийным строкам).
- Клик по наименованию всегда ведёт на карточку детали (общую для всех её
  единиц), клик по серийному номеру — на карточку конкретной единицы (там
  же управление наработкой, списанием, историей). Кнопки добавления — обе
  сразу над таблицей: «+ Новая деталь» (в справочник) и «+ Серийная
  единица» (зарегистрировать новый экземпляр под существующей деталью).

Столбец OD/ID (используется для подбора пар ротор/статор, раздел ниже) в
общем списке больше не показывается, чтобы не перегружать таблицу — он
по-прежнему виден и редактируется на карточке конкретной единицы.

## Инструмент подбора пары ротор/статор

Раздел **Подбор пар** — теперь подраздел раздела **«Сервис»** (вкладка рядом
с «Работы и затраты»; см. навигацию сайта и раздел «Сервис» ниже). Система
забирает все роторы и статоры на складе (со
статусом «на складе» и заполненными OD/ID), рассчитывает зазор для всех
комбинаций (`зазор = ID статора − OD ротора`) и оптимальным образом
сопоставляет их так, чтобы:

1. как можно больше пар попало в заданный диапазон зазора (по умолчанию
   0,2–0,3 мм, диапазон можно менять на странице);
2. среди этих пар суммарное отклонение от идеальной середины диапазона было
   минимальным.

Это классическая задача о назначениях, решается венгерским алгоритмом
(проверено на тестовых данных — алгоритм действительно находит глобально
оптимальное сочетание, а не первое подходящее). Подтверждённая пара помечает
оба компонента статусом «в паре» и сохраняется в истории.

## Единый учёт остатков (серийные детали и расходники)

Каждая деталь в справочнике учитывается одним из двух способов, но
отображается везде одинаково — одно число «текущий остаток» на дэшборде, в
справочнике, в аналитике и в прогнозе (см. `app/stock.py`):

- **По серийным номерам** (роторы, статоры, корпусные детали и т.п.) —
  остаток = количество карточек-единиц в статусе «на складе».
- **По количеству** (масло, уплотнения, кольца и другие расходники) —
  остаток = остаток на фиксированную дату среза (01.08.2026, дата самых
  свежих исторических поступлений в исходном Excel) + все поступления,
  внесённые ПОСЛЕ этой даты, − все списания, внесённые ПОСЛЕ этой даты.

Дата среза нужна только для того, чтобы не задвоить историю, уже
импортированную из Excel. Любая операция, внесённая через само приложение
(сегодня, завтра, через год), автоматически оказывается «после среза» и
корректно меняет остаток — отдельно ничего настраивать не нужно. Заводить
новую несерийную деталь вручную (кнопка «Новая деталь») можно сразу с
текущим фактическим остатком — она создаётся уже «после среза», поэтому
никакого пересчёта не требуется.

Списать расходник можно двумя способами: со страницы **Списания -> Расходник
(по кол-ву)**, либо прямо со страницы конкретной ремонтной/сборочной работы
(см. ниже) — тогда его стоимость автоматически войдёт в стоимость работы.

### Партии поступления

Одна строка поступления = одна **партия** (ввоз/поставка): для серийных
деталей — сразу на все серийные номера, ввезённые вместе одной партией, для
расходников по количеству — как и раньше, одна поставка = одна строка.
Раньше при внесении поступления сразу на несколько серийных номеров на
каждый номер создавалась своя строка поступления с задублированными
данными партии (курс, пошлина, стоимость) — теперь это одна строка на всю
партию, а привязка к конкретным серийным единицам видна списком в колонке
«Серийные №» на странице **Поступления**.

Для каждой партии, помимо количества и даты, хранятся дополнительные
справочные поля — как импортированные из листа «AGIT Spares» исходного
Excel-файла, так и вводимые вручную на странице **Поступления -> Новое
поступление**:

- **Номер партии** (`batch_serial_number`) — вводится вручную при создании
  поступления (поле «Номер партии»); при импорте из Excel заполняется из
  соответствующего столбца, а если в исходной строке номера не было —
  ставится прочерк «-». Если номер партии совпадает с серийным номером уже
  заведённого компонента (лист «AGIT components»), историческое поступление
  при импорте автоматически связывается с этой серийной единицей (см.
  `backfill_receipt_unit_links()` в `scripts/import_excel.py`).
- **Дата производства** (`date_mfg`) — как есть из Excel (например, `Aug-26`).
- **Курс юаня к рублю на момент покупки** (`exchange_rate`) — указывается
  для каждой партии отдельно (поле «Курс юаня к рублю» на форме нового
  поступления), поскольку курс на дату конкретной поставки может отличаться
  от партии к партии.
- **Общая стоимость партии, CNY** (`total_cost_cny`).
- **Трансфер прайс за единицу, ₽** (`transfer_price_rub`) — логистика/доставка сверх таможенной стоимости.

Таможенной пошлины среди справочных полей партии **намеренно нет** — в
отличие от курса и стоимости, пошлина привязана не к конкретной поставке, а
к самой ПОЗИЦИИ (`parts.customs_duty_percent`, поле «Пошлина, %» в карточке
детали) и одна и та же для всех партий этой детали независимо от того, когда
и от кого она приехала. Правится только в карточке детали (**Комплектующие**
→ деталь → «Редактировать») — форма нового поступления её не запрашивает и
не может изменить.

Эти поля отображаются дополнительными столбцами на странице **Поступления**
и в карточке несерийной детали (в общей ленте поступлений/списаний). При
ручном добавлении поступления через форму все три «справочных» поля партии
(итого CNY / курс / трансфер прайс) необязательны — но именно они, вместе с
пошлиной из карточки детали, формируют расчётную стоимость за единицу (см.
ниже).

**Остаток партии.** У каждой партии есть собственный остаток
(`remaining_quantity`) — стартует равным количеству партии и уменьшается по
мере списания именно из неё (см. «Списание с выбором партии» ниже), а при
удалении ремонтной/сборочной работы (см. «Ремонтные/сборочные работы» ниже)
или снятии компонента без списания — увеличивается обратно. Партия с
остатком 0 считается закрытой и не участвует в оценке стоимости остатка
детали и в списке партий для списания.

**Стоимость остатка комплектующих.** И в карточке детали (блок «Стоимость
остатка (по партиям на складе)»), и на дэшборде (плитка «Стоимость остатка,
₽» — сумма по всем деталям) стоимость остатка считается не по «текущей»
стоимости за единицу из карточки детали, а как сумма по ВСЕМ ещё не
закрытым партиям детали: (стоимость за единицу именно этой партии) ×
(остаток именно этой партии). Курс юаня, показанный там же, — средневзвешенный
по остатку партий (партии с бОльшим остатком сильнее влияют на средний
курс). Если часть текущего остатка детали относится к историческим данным,
для которых партия-источник не восстановлена (см. `scripts/migrate_receipt_batches.py`
ниже), в карточке детали под блоком стоимости появляется предупреждение —
сколько единиц остатка учтено в стоимости, а сколько нет.

**Списание с выбором партии.** При списании несерийного расходника — как со
страницы **Списания -> Расходник (по кол-ву)**, так и прямо со страницы
конкретной работы («Списать расходник по количеству») — появляется
выпадающий список партий этой детали с ненулевым остатком (формат «номер
партии · дата · остаток N шт»); по умолчанию выбрана самая старая партия с
остатком (FIFO), но можно выбрать любую другую вручную. Для серийного
компонента (у него всегда ровно одна партия-источник — та, в составе
которой он был оприходован) выбор не нужен: при списании партия
подставляется автоматически, остаток этой партии уменьшается на 1.
Списания, добавленные до перехода на партийную модель (или без указания
партии позднее), остаются без привязки к партии — их стоимость по-прежнему
считается по «текущей» формуле в карточке детали, но в оценку остатка по
партиям, естественно, не входят (они уже списаны).

Лист «AGIT Spares write-off» (историческое списание компонентов на сборку
конкретных инструментов) сознательно НЕ импортируется как записи списания:
эти же компоненты уже импортированы из листа «AGIT components» в статусе «в
эксплуатации», и повторное их списание создало бы противоречивое состояние
(одновременно «списан» и «установлен на инструменте»). Наработка и выручка
по каждому инструменту ведутся отдельно (см. раздел «Инструменты» ниже) и
не требуют исторических записей списания.

## Расчётная стоимость за единицу

Стоимость одной единицы детали (используется в стоимости списаний на
ремонтные/сборочные работы, см. «Сервис» ниже) считается автоматически по
формуле (`app/costing.py`):

```
Стоимость за единицу, ₽ = Себестоимость, CNY × Курс юаня к рублю
                           × (1 + Пошлина, % / 100) + Трансфер прайс, ₽
```

Составляющие формулы хранятся и правятся по-разному в зависимости от того,
может ли значение отличаться от партии к партии:

- **Пошлина (%)** — атрибут самой ПОЗИЦИИ (`part_number`), а не партии:
  правится только в **карточке детали** (раздел «Комплектующие» → деталь →
  «Редактировать») и одна и та же для ВСЕХ партий этой детали. Форма
  поступления это поле не запрашивает и повлиять на него не может — так
  сделано намеренно (см. «Партии поступления» выше).
- **Себестоимость (CNY), курс юаня к рублю, трансфер прайс (₽ за единицу)**
  — наоборот, могут отличаться от партии к партии, поэтому вводятся заново
  при каждом **поступлении** (раздел «Поступления» → «Новое поступление»);
  себестоимость партии в CNY там пересчитывается на единицу автоматически
  (общая стоимость партии делится на количество). При сохранении
  поступления с заполненными полями карточка детали автоматически
  обновляется этими же значениями («текущими» становятся данные самого
  свежего поступления, используются как значения по умолчанию, например, в
  отчёте по стоимости работ) — вручную синхронизировать ничего не нужно, а
  если какое-то поле в поступлении оставить пустым, соответствующее поле в
  карточке детали не затирается.

Рядом с текущим курсом юаня в блоке «Стоимость за единицу» показана
дополнительная справочная строка — **средний курс по всем поступлениям**
этой детали (простое, не взвешенное по количеству среднее по всем когда-либо
зарегистрированным поступлениям, где курс указан). Это ЧИСТО информационная
величина для ориентира — в самом расчёте «Стоимость за единицу» (и,
соответственно, в стоимости списаний на ремонт) не участвует, там по-прежнему
работает «текущий» курс (последнее поступление). Не путайте эту величину с
«Курс юаня, средневзв. по остатку» в блоке «Стоимость остатка» выше на той же
странице — та взвешена по остатку и считается только по ещё не закрытым
партиям (`app/stock.py`: `avg_exchange_rate_all_receipts()` против
`part_stock_value()`).

На самой карточке детали все составляющие показаны отдельно (себестоимость,
курс, пошлина, трансфер прайс), а рядом — уже посчитанная итоговая
«Стоимость за единицу». Стоимость остатка по партиям (см. «Партии
поступления» выше) для каждой партии использует ЕЁ СОБСТВЕННЫЕ себестоимость/
курс/трансфер прайс, но ОДНУ И ТУ ЖЕ (текущую, из карточки детали) пошлину —
поэтому изменение пошлины в карточке детали сразу пересчитывает стоимость
остатка по всем партиям этой детали разом.

Стоимость списанных на ремонтную/сборочную работу компонентов (раздел
«Сервис») теперь считается по этой полной формуле, а не только по одному
трансфер прайсу, как раньше.

## Инструменты (буровые компоновки с серийным номером)

Раздел **Инструменты**: каждая физическая единица инструмента (буровая
компоновка), в отличие от отдельных комплектующих внутри неё (ротор, статор
и т.п.), заводится в системе под собственным серийным номером — вручную
(«+ Новый инструмент») или автоматически при импорте из Excel (см. выше).

Наименование инструмента считается автоматически по типоразмеру (см.
`_TOOL_NAME_RULES` в `app/tools.py`) и показывается рядом с серийным номером
в списке и на карточке инструмента:

- 4 3/4" → **AGIT-4.75-IM**
- 6 3/4" → **AGIT-6.75-IM**
- 8" → **AGIT-8-IM**

На карточке инструмента также указываются дата ввода в эксплуатацию и
себестоимость инструмента, ₽ (оба поля заполняются при регистрации или
редактировании инструмента) — себестоимость нужна для расчёта начисленной
амортизации (см. ниже).

На странице инструмента:

- **Установленные компоненты** — какие серийные единицы сейчас стоят на
  этом инструменте; можно установить любой свободный компонент со склада
  (поиск по серийному номеру/названию) или снять — компонент вернётся на
  склад со статусом «на складе». (Сводного счётчика «компонентов на борту»
  в списке и на карточке больше нет — сам список установленных компонентов
  никуда не делся.)
- **Наработка инструмента** — вносится одной записью (дата + часы), и
  система автоматически прибавляет те же часы к наработке КАЖДОГО
  компонента, установленного на инструменте на момент записи (создаёт им
  зеркальные записи наработки — видно на странице конкретного компонента).
  Это и есть основной способ вести наработку серийных компонентов на
  практике: инструмент отработал N часов в скважине — все стоящие на нём
  ротор/статор/другие серийные детали получают те же N часов автоматически,
  без ручного дублирования по каждому компоненту.
- **Выручка** — записи о выручке, заработанной этим конкретным инструментом
  (серийным номером). Два способа внесения:
  - **вручную** (как раньше) — дата и сумма, без привязки к заказчику;
  - **с выбором заказчика** (см. раздел «Заказчики» ниже) — выбираете
    заказчика из справочника, система сама подставляет его ставки (₽/час
    работы, ₽/сутки ожидания) и даёт поля для номера скважины, часов работы
    и суток дежурства; сумма выручки считается автоматически (часы × ставка
    часа + сутки × ставка суток), а часы работы **сразу переносятся в
    наработку инструмента** — ровно так же, как обычная запись наработки
    (см. выше), включая зеркалирование на все установленные компоненты.
    Такую запись выручки нельзя отредактировать (только удалить и внести
    заново) — удаление корректно откатывает и перенесённую ею наработку.
- **Работы по этому инструменту** — все ремонтные/сборочные работы (см.
  ниже), привязанные к серийному номеру инструмента, с их стоимостью.
- **Стоимость ремонтов** (бывшее «Затраты на работы») — сумма стоимости
  всех работ, привязанных к этому инструменту.
- **Начисленная амортизация** — 1/18 себестоимости инструмента (`cost_rub`)
  за каждый ПОЛНЫЙ календарный месяц с даты ввода в эксплуатацию
  (`commissioned_date`), не более 18 месяцев (то есть не более полной
  себестоимости — после 18 месяцев инструмент считается полностью
  самортизированным, и амортизация дальше не растёт). Считается на дату
  сегодня и пересчитывается на каждой загрузке страницы — отдельно вносить
  или пересчитывать её не нужно (см. `app/tools.py`: `tool_depreciation()`).
  Если у инструмента не заполнена себестоимость и/или дата ввода в
  эксплуатацию, амортизация не считается (0, с пометкой «не задана
  себестоимость и/или дата ввода») — заполните оба поля в карточке
  инструмента, чтобы амортизация начала считаться.
- **Рентабельность** = выручка − (начисленная амортизация + стоимость
  ремонтов) — считается и обновляется автоматически, видна и в списке
  инструментов, и на странице каждого из них.

## Заказчики

Раздел **Заказчики** — подраздел **«Инструменты»** (вкладка рядом со
«Список инструментов»): справочник заказчиков со ставками, которые
подтягиваются автоматически при внесении выручки по инструменту (см.
«Выручка» в разделе «Инструменты» выше). У каждого заказчика:

- **название** и **номер договора**;
- **стоимость работы, ₽/час** — ставка, применяемая к часам работы,
  введённым на форме выручки;
- **стоимость ожидания, ₽/сутки** — ставка, применяемая к суткам
  дежурства/ожидания.

Список показывает и накопленную выручку по каждому заказчику (сумма всех
записей `tool_revenue`, где он выбран, по всем инструментам). Ставки,
применённые при внесении конкретной записи выручки, «замораживаются» на
самой этой записи (не пересчитываются задним числом) — поэтому изменение
ставки в карточке заказчика влияет только на новые записи выручки, а уже
внесённые сохраняют те ставки, что действовали на момент внесения.

## Ремонтные/сборочные работы и отчёт по затратам

Раздел **Сервис** (бывший «Работы и затраты» — переименован; внутри него же
теперь и подраздел «Подбор пар», см. выше) → вкладка **«Работы и затраты»**:
каждая работа (ремонт, сборка или другое)
обязательно привязывается к конкретному инструменту (серийному номеру) из
реестра **Инструменты** — при создании работы инструмент выбирается из
выпадающего списка, свободный текст больше не используется. У работы есть
дата, номер наряд-заказа, исполнитель (супервайзер), наименование
сервисного центра и три статьи расходов, вводимые вручную (стоимость услуг
сервисного центра, персонал, прочее).

На работу можно списать компоненты двумя способами:

- как обычно — со страницы созданной работы (поиск серийного компонента
  или списание расходника по количеству);
- либо — если компонент уже был списан раньше (например, через раздел
  «Списания», ещё до того, как оформили саму работу) — прямо на форме
  **создания** новой работы есть окно «Списанные комплектующие» со списком
  ещё не привязанных ни к одной работе списаний; отметьте нужные, и они
  свяжутся с работой сразу при её создании.

Поиск серийного компонента для списания на странице работы находит не
только свободные компоненты на складе, но и компоненты, уже **установленные
на инструменте этой работы** — например, когда ремонт как раз состоит в
замене стоящего компонента. Для такого найденного компонента показываются
две кнопки: **«Списать»** (компонент признаётся дефектным, статус —
«списан», привязка к инструменту снимается) и **«Перевести на склад»**
(компонент просто снимается с инструмента и возвращается на склад со
статусом «на складе», без списания — например, при плановой замене
исправного компонента). Для компонентов, уже лежащих на складе, доступна
только «Списать», как раньше.

Удалить саму работу может только администратор — кнопка «Удалить работу»
на странице работы. При удалении работы её списания отменяются: серийный
компонент возвращается на склад (статус снова «на складе», привязка к
инструменту снимается), а у несерийного расходника остаток партии-источника
(см. «Партии поступления» ниже) увеличивается обратно на списанное
количество — сами записи списания при этом удаляются вместе с работой.

Стоимость деталей считается автоматически по расчётной стоимости за единицу
(себестоимость × курс юаня × (1 + пошлина) + трансфер прайс — см. раздел
«Расчётная стоимость за единицу» выше) и складывается с остальными статьями
в общую стоимость работы, которая, в свою очередь, засчитывается в затраты
(«Стоимость ремонтов») того инструмента, к которому привязана работа (см.
«Инструменты» выше).

Раздел **Отчёт по затратам** агрегирует все работы за период (фильтры по
типу и датам): количество работ, стоимость деталей отдельно от сервисного
центра/персонала/прочего, разбивка по типу работы (диаграмма) и выгрузка в
CSV.

## Аналитика и прогноз заказа

Раздел **Аналитика** содержит две вкладки:

- **Списания по периодам** (прежняя главная страница раздела) — расход
  (списания) по деталям и периодам (месяц/квартал) с разбивкой по причине
  (ремонт/брак/повреждение), фильтры по детали и типоразмеру. Считается по
  количеству (`quantity`), поэтому расходники, списанные сразу пачкой,
  учитываются корректно, а не как «одно списание».
- **Сводный отчёт** (`/analytics/report`) — шесть показателей одним экраном:
  - **остаток комплектующих на складе, ₽** — та же величина, что и на
    дэшборде (сумма стоимости остатка по всем деталям и их партиям, см.
    «Партии поступления» выше);
  - **средняя наработка на инструмент, ч** — суммарная наработка
    (`tool_usage_logs`) каждого инструмента, усреднённая по всем
    зарегистрированным инструментам;
  - **средняя наработка на компонент, ч** — `circulation_hours`, усреднённая
    по всем серийным компонентам (`units`);
  - **общая выручка на все инструменты, ₽** — сумма всех записей
    `tool_revenue` (и внесённых вручную, и через заказчика);
  - **общие затраты, ₽** — сумма стоимости всех ремонтных/сборочных работ
    (та же величина, что в «Отчёте по затратам» раздела «Сервис», но по всем
    работам, а не по одному инструменту);
  - **результат за период** — выручка минус затраты.

  Остаток склада и обе средние наработки — всегда **на текущий момент**
  (это накопленное состояние, а не событие с датой, которое имело бы смысл
  резать по периоду). Выручка и затраты, наоборот, считаются **за выбранный
  период** — фильтр «с» / «по» над отчётом, как в «Отчёте по затратам»
  раздела «Сервис»; без дат — показатели за всё время.
- **Прогноз заказа** — подраздел раздела **«Комплектующие»** (кнопка
  «Прогноз заказа» в шапке этого раздела). Для КАЖДОЙ детали справочника
  (серийной и количественной одинаково): средний месячный расход за последние
  N месяцев (по умолчанию 6, настраивается) × 3 месяца вперёд, минус текущий
  остаток (см. «Единый учёт остатков» выше), с учётом неснижаемого запаса.
  Результат можно выгрузить в CSV.

Все страницы опираются на реальную историю операций в системе — сразу после
разворачивания истории ещё нет (см. раздел про импорт выше), поэтому графики
и показатели заполнятся по мере внесения операций.

## Известные ограничения и рекомендации по доработке

- **Стили через CDN**: Tailwind CSS и Chart.js подключены как публичные CDN
  (без сборки) — это стандартный и рабочий подход для внутреннего сервиса
  такого масштаба, но для более "production-grade" результата (быстрее
  загрузка, работа без внешних CDN) в будущем стоит собрать статический
  Tailwind-бандл через `npx tailwindcss` и подключить локально.
- **Восстановление пароля по email не реализовано** — пользователь может
  сменить свой пароль сам (зная текущий) через «Смена пароля» в правом
  верхнем углу; если пароль забыт полностью, администратор задаёт новый
  через `scripts/create_admin.py` (перезаписывает пароль по email). Для
  полноценного продакшна стоит добавить сброс пароля по ссылке на email
  (напр. через Resend/Postmark — у обоих есть бесплатный тариф и
  Vercel-интеграция).
- **Стоимость деталей в отчёте по работам** — считается по расчётной
  стоимости за единицу (себестоимость CNY × курс × (1 + пошлина) + трансфер
  прайс, см. «Расчётная стоимость за единицу» выше). У части импортированных
  деталей составляющие формулы не заполнены (нет данных в исходном Excel) —
  такие строки просто не добавляют сумму в стоимость работы; заполните их
  вручную (редактирование детали или новое поступление), когда они станут
  известны.
- **Оценка остатка по партиям — только для того, что реально прослежено до
  партии.** Историческая часть остатка (импортированная как «остаток на
  начало» без привязки к конкретной поставке) не входит в расчёт стоимости
  остатка по партиям — см. предупреждение в карточке детали и раздел
  «Партии поступления» выше. Если нужна полная оценка остатка целиком,
  внесите для такой детали недостающие исторические поступления вручную —
  тогда остаток по ним тоже начнёт учитываться.
- **Наработка и OD/ID** — по-прежнему ведутся только для серийных деталей
  (это то, что физически применимо только к конкретным пронумерованным
  компонентам вроде ротора/статора); для расходников эти поля не нужны.
  Наработку конкретного компонента можно вносить как вручную (на странице
  самого компонента), так и через наработку инструмента, на котором он
  установлен (см. «Инструменты» — это основной способ и рекомендуемый путь
  на практике, поскольку не требует дублирования часов по каждому
  компоненту отдельно).
- **Один инструмент установлен только на одном компоненте за раз** — если
  компонент нужно переставить на другой инструмент, сначала снимите его с
  текущего (кнопка «Снять» в списке установленных компонентов), затем
  установите на новый; система не позволяет числиться установленным на двух
  инструментах одновременно (это отражает физическую реальность — деталь
  физически не может стоять в двух местах сразу).
- **Права доступа** — сейчас общий склад с ролями (как выбрано при
  постановке задачи). Если позже понадобится несколько независимых
  организаций на одной инсталляции — потребуется добавить поле

  
  `organization_id` в таблицы и фильтрацию по нему (архитектурно
  закладывается без проблем).
